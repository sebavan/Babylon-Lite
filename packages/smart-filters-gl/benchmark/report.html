On a real GPU both stacks render pixel-equivalent output (99.6% byte-identical, mean Δ 0.18/channel — the rest is sub-texel rounding at pixelate cell boundaries), while the port ships 6–8× less code. Trade-offs are spelled out below, not glossed.

3Pixel parity

99.6% byte-identicalmean Δ 0.18 / channel512×512 · intensity 0.6 · NEAREST

Both stacks render the identical pixelate fragment (mix(256,8,intensity) UV-snap); the port's shim only translates the dialect (GLSL ES 1.0 → 3.00). Rendered on the same real GPU (NVIDIA RTX 2080 Ti) with the same deterministic input and matched sampling, the outputs are 99.61% byte-identical (per channel), mean absolute difference 0.18/255. The remaining ~0.4% of pixels sit on pixelate cell boundaries, where the non-integer grid (107.2 cells across 512 px) rounds to a neighbouring texel differently between the two engines — sub-texel, not a fidelity gap.

Columns 2 & 3 are the two engines rendering the same effect — visually indistinguishable. Column 4 shows a two-block graph (each non-final block gets its own render target), proving multi-block chaining.

Per-frame JS cost is tiny on both (a single fullscreen draw) — well under 0.1% of a 16 ms budget — so the ~3× difference is negligible in absolute terms; the real win is bundle size, not frame time. One robustness note: lite-gl effects reset to not-ready (empty uniform locations) on a WebGL context loss/restore. The port re-validates readiness every frame in _draw, so it keeps rendering after a GPU reset / tab-restore — a fix found and added during validation (it also kept the port rendering under headless SwiftShader's frequent context-loss, where the stock runtime stalled).

Method: Playwright headed, real GPU (no SwiftShader). JS/frame = median over 300 frames of the synchronous render() submit cost (GPU work runs in parallel). Init & heap are run-to-run noisy (shader-compile bound); ranges shown.

The shader shim (the crux)

SmartFilter blocks are authored in GLSL ES 1.0 (texture2D, gl_FragColor, varying vUV); Babylon auto-converts them. lite-gl's createEffect wants raw GLSL ES 3.00, so the port's GetShaderCreateOptions assembles ES 3.00 — #version 300 es + precision, in vec2 vUV, out vec4 glFragColor, texture2D→texture, plus a matching fullscreen-quad vertex shader. The graph, blocks, connections and command buffer port across essentially unchanged (27 files · 2,476 LOC).

6Trade-offs

What you gain

  • 6–8× smaller bundle — 30.6 KB min / 9.7 KB gzip vs 233 / 60 KB.
  • Tiny engine surface — 9 lite-gl modules (16 KB) vs 64 core modules (215 KB).
  • Pixel-equivalent output — 99.6% byte-identical to Babylon on the same GPU.
  • Same authoring model — blocks, connections, ShaderCode, createRuntimeAsync unchanged; existing GLSL-1 blocks port via the shim.
  • Function-based + tree-shakeable; context-loss resilient.

What you give up (for now)

  • WebGL2 only — no WebGPU; no WebGL1 fallback.
  • POC scope — optimizer, serialization, aggregate & custom blocks, and the editor layer are not ported.
  • Two example blocks — Pixelate + BlackAndWhite; the full block library is not ported.
  • Manual uniform setters — no setBool (use setEffectInt 0/1); setters are no-ops until the effect is ready.
  • Unverified at scale — large multi-pass graphs & the non-pooled render-target path are untested.

Methodology. Size: esbuild --bundle --minify --format=esm, gzip-9 / brotli-11, identical entry on both sides. Composition: esbuild metafile, bytes-in-output per input module. Render / parity / runtime: Playwright headed on a real GPU (NVIDIA RTX 2080 Ti, ANGLE/D3D11), deterministic 512×512 XOR input, Pixelate intensity 0.6, NEAREST sampling, matched orientation. Parity = per-channel byte diff over all 262 144 pixels. Baseline @babylonjs/smart-filters + @babylonjs/core v9.14.0.

Honesty notes. GPU rasterization throughput is not isolated — the JS/frame figure is CPU submit time (GPU runs in parallel); both are negligible per frame. Init/heap are run-to-run noisy (shader-compile bound) so ranges are shown. The ~0.4% non-identical pixels are sub-texel boundary rounding from the non-integer pixelate grid, not an algorithmic difference. smart-filters-gl is a proof-of-concept port, not production-complete.
